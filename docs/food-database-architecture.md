# Nutivili AI — scalable food database architecture

Status: implemented (tiers 1–3 below). Tier 4 is evaluated, not built.

## The problem

All of Nutivili's food data ships to the phone as two JSON files, searched in memory:

| File | Records | Size (raw / gzipped) | Notes |
|---|---|---|---|
| `public/data/foods.json` | 21,711 (17,793 measured foods + 3,918 standard-recipe dishes) | 6.5 MB / 1.6 MB | loads first; precached for offline use |
| `public/data/foods-more.json` | 5,209 (1,729 newer dishes + 3,480 vegan / vegetarian / other-protein versions) | 3.2 MB / 0.6 MB | loads right after |

The offline cache refuses any single file over 8 MB (`vite.config.ts`), and every phone downloads and indexes the whole set. That works for tens of thousands of curated records. It cannot work for millions: Open Food Facts alone returned 6,177 matches for "greek yogurt" in testing.

## The design: three tiers, searched in order

```
 phone                                   our server (/api/foods)                 external sources
 ─────                                   ───────────────────────                 ────────────────
 1. curated database  ── offline,        2. edge cache (Vercel, 1 day)    ──►  USDA FoodData Central
    instant, our dishes                     Supabase cache (7 days)              (Branded, Foundation,
    (unchanged)                             indexed store of every food           FNDDS, SR Legacy)
                                            ever returned                    ──►  Open Food Facts
 + foods already used, kept on            de-duplicated, labelled, paged
   the phone (remoteFoods)
 + recent result pages (3 days)
```

1. **Curated database: ours, on the phone.** International dishes, African foods, regional recipes, their versions, spice blends, and each user's custom foods and meals. It is untouched by this change and stays the first thing searched, offline and instant.
2. **Unified external search: `/api/foods`.** Searches USDA FoodData Central and Open Food Facts at the same time and merges the results. It covers branded and supermarket products, restaurant items, generic ingredients and survey meals. Only results the user asks for are fetched (they appear when local results are thin, or on tap), one page at a time, with "Load more".
3. **Caching at three levels**, so a popular food never needs the same external call twice:
   - Edge: responses carry `s-maxage=86400, stale-while-revalidate=604800`, so Vercel's CDN answers repeat queries without running the function.
   - Server: with `supabase/food-cache.sql` run, each result page is kept 7 days (`food_search_cache`). Every food returned is stored in `external_foods`, which has a full-text index (GIN on a tsvector), a trigram index on names and a barcode index. When both sources are down, search falls back to this table.
   - Phone: the last 40 result pages are kept 3 days. Any external food a person logs or opens is kept for good (works offline, no new lookup).
4. **Not built: bulk import (tier 4).** See the evaluation below.

### Barcodes

`/api/foods?barcode=…` tries Open Food Facts, then USDA Branded Foods (matched on `gtinUpc`), then the server's own `external_foods` table. The phone first checks products it has scanned before, so repeat scans work offline. If our server isn't reachable, the app asks Open Food Facts directly.

### Duplicates and preparation

- Within external results, one entry per real food. The same barcode from both sources is one product, with USDA preferred. So is the same name with the same energy (within 5 kcal).
- External results that are already in the curated database (same USDA record) are hidden in favour of the curated copy.
- Each external food gets a raw / cooked / dry state, and a cooking method when its name says so: fried, grilled, roasted, baked, boiled, steamed, stewed, smoked, sautéed. Fried and grilled versions are never merged.
- The curated database already keeps raw and cooked records separate and merged its identical twins earlier.

### Where every number comes from

Every food shows its source and how much to trust it (`dataQuality` / `sourceInfo` in `src/lib/foods.ts`):

| Source | Shown as | Level |
|---|---|---|
| USDA SR Legacy, FNDDS, Foundation; FAO/INFOODS; UK CoFID; AFCD | official food composition table / lab-analysed | measured |
| USDA Branded Foods, Open Food Facts | from the manufacturer's / pack label — check it matches yours | label |
| Nutivili standard recipes and versions | calculated from a standard recipe of measured ingredients | calculated |
| User entries | your own numbers | yours |

**Nutrient values are never generated by AI.** AI only estimates portion weights from photos, and those diary entries are marked "Portion estimated by AI". No AI-made food record exists in any tier.

## Evaluation before any bulk import

The brief asked for this evaluation before anything large is inserted. Conclusion: **don't bulk-import now.** On-demand caching (tier 3) gives access to the full catalogues and stores only what people actually look up.

| Question | Finding |
|---|---|
| Storage | A normalised food is about 1–2 KB in `external_foods`. 100,000 cached foods ≈ 150 MB; 1 million ≈ 1.5 GB plus indexes, very roughly 2–3 GB. Supabase's free plan (500 MB) would fill quickly; its Pro plan includes 8 GB. A full mirror of both sources would need full nightly sync jobs and many GB. |
| Indexing | Postgres full-text (GIN) plus trigram (`pg_trgm`) indexes answer name searches over millions of rows in tens of milliseconds when the query uses the index. The SQL above creates them. A dedicated search engine (Typesense / Meilisearch / Elastic) is only worth it past several million rows or for typo-heavy ranking. |
| Search performance | Phone-side search stays instant for curated foods. External pages cost one round trip (≈0.3–1.5 s uncached, ≈50 ms from the edge cache). Pages are 20 results. |
| Hosting cost | Edge-cached responses don't run the function. A commercial app should be on Vercel Pro rather than Hobby (Hobby is for non-commercial use). Supabase Pro covers the cache comfortably. Check current prices before deciding; they change. |
| Rate limits | USDA: 1,000 requests/hour per key. Open Food Facts: 100 product reads/minute, and search is stricter: a second search page seconds after the first was refused in testing. All calls come from our server, so the caches above protect these limits. |
| Licensing | See below. Open Food Facts' share-alike licence is the main reason not to merge its data into the curated database. |

**Revisit bulk import when:** daily external lookups exceed what the caches absorb (watch the USDA 1,000/hour limit), or offline search of branded products becomes a must-have. Then mirror only USDA Branded (public domain, no share-alike) into `external_foods` with a nightly job, and keep Open Food Facts live and on-demand.

## What the owner has to do

1. **Get a free USDA key** at https://fdc.nal.usda.gov/api-key-signup. In Vercel → Project → Settings → Environment Variables, add `USDA_API_KEY` and redeploy. Without it the shared `DEMO_KEY` is used, which is heavily rate-limited (it was already blocked during testing). Never put the key in code or chat.
2. **Optional but recommended:** run `supabase/food-cache.sql` in the Supabase SQL editor. It turns on the 7-day result cache, the indexed store and the fallback when sources are down. Everything works without it, using only the edge and phone caches.
3. Once a week, run `delete from public.food_search_cache where expires_at < now();` (or schedule it).

## Code map

- `api/_lib/foodSources.ts`: USDA and Open Food Facts clients and normalisers, preparation detection, de-duplication.
- `api/_lib/foodSearch.ts`: the `/api/foods` handler: paging, caching, barcode, attribution. It is served by `api/photos.ts` through a `vercel.json` rewrite (the plan allows 12 functions).
- `src/lib/foodSearch.ts`: the phone side: calls `/api/foods`, keeps recent pages, falls back to Open Food Facts directly, hides foods already in the curated database.
- `supabase/food-cache.sql`: cache and index tables.
- `api/_tests/foods.test.ts`: normalising, merging, paging, outages, barcodes.

## About "1,000 dishes in every country"

The curated tier keeps growing country by country with real, documented dishes, and the completion tracker (Owner dashboard) shows each country's progress. The external tier is what gives people access to millions of foods, including every branded and restaurant item those databases hold. A curated country count of 1,000 is still the goal, but it will only be reached with real dishes, never padded ones.
